# API Gateway Kafka Microservice Design

## Goal

Refactor this repository from a feature-owning HTTP API into an API Gateway for
a microservice system.

The gateway is the only service called directly by clients. It owns HTTP-facing
concerns such as request validation, authentication, routing, response mapping,
and operational health endpoints. Business services own domain behavior and
communicate through Kafka.

## Target Architecture

```text
Client
  |
  | HTTP / WebSocket
  v
API Gateway
  |
  | Kafka commands / replies
  v
Business Services
  |
  | Kafka events
  v
Other Business Services
```

The gateway may expose HTTP endpoints for clients and health checks. It must not
own feature persistence, image processing, domain entities, or business database
tables.

## Repository Role

This repository becomes `api-gateway`.

It will:

- Receive client requests over HTTP.
- Validate and normalize request DTOs.
- Authenticate callers where required.
- Publish Kafka commands to business services.
- Optionally wait for Kafka replies when an HTTP request needs a synchronous
  response.
- Keep liveness and readiness endpoints for deployment.

It will not:

- Keep the current `files` feature as gateway-owned business logic.
- Own MikroORM entities, migrations, or feature repositories.
- Call other service databases directly.
- Import business-service internals.

## Kafka Communication Model

Use topic categories by intent:

```text
*.commands  = request another service to do work
*.events    = announce something that happened
*.replies   = return a result for request/reply flows
```

Initial naming convention:

```text
stream.commands
stream.events
stream.replies
```

Command messages should include:

- `requestId`: correlation ID generated by the gateway.
- `userId`: authenticated actor when available.
- `type`: command name, for example `stream.create`.
- `payload`: command-specific data.

Reply messages should include:

- `requestId`: same value from the command.
- `ok`: boolean result marker.
- `data`: success payload when `ok` is true.
- `error`: stable error object when `ok` is false.

Event messages should represent completed facts, not instructions. For example,
`stream.created` is an event; `stream.create` is a command.

## Gateway Module Shape

The first gateway module should be a thin `streams` HTTP-to-Kafka adapter:

```text
src/
|-- main.ts
|-- app.module.ts
|
|-- infrastructure/
|   |-- config/
|   |-- kafka/
|   `-- health/
|
|-- modules/
|   `-- streams/
|       |-- application/
|       |   `-- use-cases/
|       |-- presentation/
|       |   |-- http/
|       |   |   `-- dto/
|       |   `-- kafka/
|       `-- streams.module.ts
|
`-- shared/
    |-- application/
    `-- presentation/
```

The `streams` module exists only as the gateway contract example. It should not
contain stream domain models or stream persistence. Those belong in a separate
`stream-service`.

## Runtime Design

The gateway remains an HTTP NestJS application because clients call it over
HTTP. Kafka is used as an outbound transport to business services.

Use NestJS `ClientsModule` with Kafka transport for gateway-to-service
communication. Wrap Kafka access in a small gateway-owned service so
controllers do not depend directly on Kafka client details.

Keep business handlers out of this repository. `@MessagePattern` and
`@EventPattern` belong in business services, not the API Gateway, unless the
gateway later needs to consume replies through a dedicated adapter.

## Current Module Removal

Remove the existing `files` module and related storage/image concerns from the
gateway:

- `src/modules/files/**`
- feature-specific MikroORM entity and migration references
- local file storage adapter
- upload/image-processing dependencies when no remaining code needs them
- file upload E2E tests
- README sections describing the files feature

Keep generic shared infrastructure only if still used by the gateway.

## Configuration

Required gateway configuration:

```env
APP_NAME=api-gateway
APP_PORT=3000
NODE_ENV=development
KAFKA_BROKERS=localhost:9092
KAFKA_CLIENT_ID=api-gateway
KAFKA_GROUP_ID=api-gateway
JWT_SECRET=change-this-secret-before-deployment
TOKEN_EXPIRATION=1000d
```

Database configuration should be removed from the gateway unless a future
gateway feature has a clear operational need for gateway-owned persistence.

## Docker Compose

Local Compose should run:

- `api-gateway`
- Kafka broker

PostgreSQL and migrator services should be removed from this repository's local
Compose file after the files module is removed.

Kafka should be configured for local single-node development. Production Kafka
topology is environment-owned and should be supplied through `KAFKA_BROKERS`.

## Error Handling

HTTP controllers map gateway validation errors and downstream reply errors into
stable HTTP responses.

Gateway responses should not expose raw Kafka, stack trace, or internal service
error details. Downstream service errors must be normalized into public error
codes and messages.

Timeouts are required for request/reply flows. If a downstream service does not
reply in time, the gateway returns a timeout response instead of holding the
HTTP connection indefinitely.

## Health And Deployment

Keep HTTP operational endpoints:

```text
GET /health/live
GET /health/ready
```

Liveness verifies that the process is running. Readiness verifies required
runtime dependencies, especially Kafka connectivity.

Enable NestJS shutdown hooks so deployments close HTTP and Kafka connections
gracefully.

## Testing

Test coverage should focus on gateway behavior:

- controller validation and response mapping
- use cases publishing the expected Kafka command envelope
- timeout/error mapping for request/reply flows
- health endpoints

Business behavior belongs in business-service tests, not gateway tests.

## Migration Strategy

1. Remove files feature and database-owned code from the gateway.
2. Add Kafka client infrastructure and validated Kafka configuration.
3. Add a minimal `streams` gateway module as the reference HTTP-to-Kafka flow.
4. Update Docker Compose to run Kafka and the gateway.
5. Update README with the API Gateway role, Kafka topic conventions, and local
   run instructions.
6. Run unit tests, E2E tests, lint, build, and Docker Compose validation.

## Out Of Scope

- Implementing `stream-service`.
- Implementing Kafka consumers for business commands in this repository.
- Sharing databases between services.
- Adding CQRS, event sourcing, or saga orchestration before a real workflow
  requires it.
- Keeping the old files upload feature inside the gateway.
